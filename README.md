# Черновик карточки товара для B2B-магазина КИП

Прототип сервиса: на вход — данные о контрольно-измерительном приборе (JSON или веб-форма),
на выход — черновик карточки товара для контент-менеджера:

- SEO-заголовок до 70 символов;
- SEO-описание 800–1200 символов;
- структурированный список характеристик (значения — только из входных данных, иначе «данных нет»);
- 3–5 поисковых запросов;
- коммерческий блок для менеджера: кому подходит прибор и какие задачи решает;
- список полей, которые нужно уточнить, и предупреждения автоматической проверки.

Главная идея решения — **модели не доверяем на слово**: каждый ответ проверяется кодом
(все значения характеристик дословно найдены во входных данных, в текстах нет чужих чисел и «рискованных»
утверждений, соблюдены длины), при нарушениях модель получает список замечаний и исправляет ответ.
Подробнее — в разделе [Как исключаются выдуманные характеристики](#как-исключаются-выдуманные-характеристики).

## Быстрый старт

Нужен Python 3.10+ и ключ любого OpenAI-совместимого API (OpenAI, OpenRouter, локальный llama.cpp/vLLM/Ollama).

```bash
git clone <repo> product-card-generator && cd product-card-generator
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                                 # вписать LLM_API_KEY (и при необходимости LLM_BASE_URL, LLM_MODEL)
```

Переменные окружения (файл `.env` в `.gitignore`, ключа в коде нет):

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `LLM_API_KEY` | — | ключ API (обязательно) |
| `LLM_BASE_URL` | `https://api.openai.com/v1` | адрес OpenAI-совместимого API |
| `LLM_MODEL` | `gpt-4.1-mini` | модель |
| `LLM_TEMPERATURE` | `0.2` | температура генерации |
| `LLM_TIMEOUT` | `60` | таймаут запроса, с |
| `LLM_MAX_ATTEMPTS` | `3` | максимум обращений к модели на один товар (первый + исправления) |
| `LLM_JSON_MODE` | `1` | просить `response_format=json_object`; при ошибке сервера отключается автоматически |

Локальная модель, например llama.cpp: `LLM_BASE_URL=http://127.0.0.1:8080/v1 LLM_API_KEY=local LLM_MODEL=qwen`.

### CLI

```bash
python -m app.cli examples/input/manometer_dm02.json              # Markdown в stdout
python -m app.cli examples/input/manometer_dm02.json --format json
python -m app.cli examples/input/*.json --out-dir out/ -v         # <имя>.json и <имя>.md для каждого файла, лог попыток
```

Коды выхода: `0` — успех, `1` — ошибка входных данных или генерации (подробности в stderr), `2` — не задан ключ.

### Веб-форма и API

```bash
uvicorn app.web:app --reload
```

- http://127.0.0.1:8000 — форма: название, производитель, характеристики (по одной на строку), описание
  или готовый JSON. Результат показывается как Markdown и JSON, копируется кнопкой.
- `POST /api/generate` — JSON о товаре → `{"card": {...}, "markdown": "..."}`.
- `GET /api/health` — модель и адрес API, с которыми работает сервис.
- `GET /docs` — Swagger.

```bash
curl -s http://127.0.0.1:8000/api/generate -H 'Content-Type: application/json' \
  -d @examples/input/manometer_dm02.json | python -m json.tool
```

## Формат входных данных

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

Обязательно только `name`. Пустые `manufacturer`/`description`, пустые значения в `specs` (`""` или `null`)
допустимы — они попадут в список «требует уточнения».

## Формат результата

JSON (`card`) — для интеграции, Markdown — для копирования в CMS.

```jsonc
{
  "product": {"name": "...", "manufacturer": "..."},
  "seo_title": "...",                          // ≤ 70 символов
  "seo_description": "...",                    // 800–1200 символов
  "characteristics": [                         // status: ok — из входных данных, missing — «данных нет»
    {"name": "диапазон измерений", "value": "0–1,6 МПа", "status": "ok"},
    {"name": "степень защиты", "value": "данных нет", "status": "missing"}
  ],
  "search_queries": ["...", "..."],            // 3–5
  "commercial_block": {"for_whom": "...", "tasks": ["...", "..."]},
  "missing_fields": [{"field": "...", "comment": "..."}],   // что уточнить у поставщика
  "quality": {
    "seo_title_length": 41, "seo_description_length": 987,
    "attempts": 2,                             // сколько обращений к модели понадобилось
    "warnings": []                             // что менеджеру стоит проверить вручную
  },
  "meta": {"model": "...", "generated_at": "...", "prompt_tokens": 1234, "completion_tokens": 567}
}
```

Примеры для двух товаров — в [`examples/`](examples/): входные файлы в `input/`, результаты
в `output/` (модель `gpt-4.1-mini`) и `output-local-qwen/` (локальная Qwen3.6-35B-A3B через llama.cpp —
для проверки, что решение не привязано к провайдеру). Второй товар намеренно с пробелами в данных
(пустые характеристики, нет описания).

## Как исключаются выдуманные характеристики

Три уровня защиты (код — `app/validation.py`, `app/service.py`):

1. **Промпт** (`app/prompts.py`): единственный источник фактов — входные данные; значения копировать дословно;
   запрещены пересчёт единиц, стандарты, материалы, гарантии, сертификаты и т.п., если их нет в данных;
   отсутствующее — ровно «данных нет»; без маркетинговых обещаний.
2. **Проверка ответа кодом** — после каждого ответа модели:
   - значение каждой характеристики (после нормализации тире, десятичных запятых, пробелов) должно дословно
     встречаться во входных данных либо быть «данных нет»;
   - все характеристики из входных данных должны попасть в карточку (полнота);
   - в заголовке, описании, запросах и коммерческом блоке не должно быть чисел, которых нет во входных данных
     (так ловятся «гарантия 2 года», «IP54», пересчёт МПа → бар);
   - «рискованные» утверждения (ГОСТ, ТУ, IP, EN/ISO/DIN, Госреестр СИ, сертификация, поверка, гарантия,
     срок службы, взрывозащита, материалы, кислородное исполнение) и оценочные эпитеты («надёжный»,
     «долговечный», «лучший»…) допустимы только если есть во входных данных;
   - длины: заголовок ≤ 70, описание 800–1200, запросов 3–5, не больше 6 строк «данных нет» от модели.
3. **Исправление и страховка**: при нарушениях модель получает их список и возвращает исправленный JSON
   (до `LLM_MAX_ATTEMPTS` обращений). Если нарушения остались, код чинит то, что можно чинить безопасно
   (непроверяемое значение заменяется исходным из входных данных или на «данных нет», пропущенные характеристики
   добавляются), а остальное попадает в `quality.warnings` — менеджер видит, что проверить вручную.

## Обработка некорректных и неполных данных

| Ситуация | Поведение |
|---|---|
| Некорректный JSON в файле / теле запроса | CLI: сообщение с позицией ошибки, код `1`; API: `400` |
| Нет `name`, `specs` не объект | CLI: понятное сообщение, код `1`; API: `422` со списком ошибок |
| Нет производителя / описания, пустые значения характеристик | Генерация идёт, поля попадают в `missing_fields` и показываются как «данных нет» |
| Модель вернула не JSON / не ту структуру | Повторный запрос с описанием ошибки; если все попытки неудачны — `GenerationError` (API: `502`) |
| Ошибки API: 401, 404 (модель/адрес), 429, таймаут, сеть | Понятные сообщения; сетевые ошибки, 429 и 5xx SDK повторяет сам |
| Сервер не поддерживает `response_format` | Автоматический повтор без него, JSON извлекается из текста (в т.ч. из ```json-обёртки) |
| Не задан ключ | CLI: код `2`; веб: сервис стартует, запрос вернёт `500` с подсказкой |

## Тесты

```bash
pytest
```

29 тестов без обращения к сети: нормализация и проверка фактов, полнота характеристик, лимиты длин,
цикл «ответ → замечания → исправление», безопасные правки, разбор входных файлов, HTTP API (ошибки 400/422/502).
LLM подменяется фейковым клиентом с заранее заданными ответами.

## Структура проекта

```
app/
  config.py      настройки из окружения / .env
  schemas.py     pydantic-модели: вход, ответ модели, итоговая карточка
  prompts.py     системный промпт, запрос, сообщение с замечаниями
  llm.py         OpenAI-совместимый клиент с понятными ошибками
  validation.py  проверки фактов, полноты, длин; безопасные правки
  service.py     цикл генерация → проверка → исправление → карточка
  render.py      Markdown / JSON
  cli.py         командная строка
  web.py         FastAPI: форма и API
  templates/index.html
examples/        входные данные и результаты для двух товаров
tests/
```
