# Промпты, принятые решения, ограничения

## 1. Промпты

Промпты лежат в `app/prompts.py`; ниже — их смысл и ключевые фрагменты.

### Системный промпт

Роль — редактор каталога B2B-магазина КИП, который готовит **черновик** (не финальную карточку).
Основной блок — правила «ничего не выдумывать», сформулированные как запреты с конкретными примерами,
потому что общее «не галлюцинируй» модели выполняют хуже, чем перечень того, что именно нельзя дописывать:

```
ГЛАВНОЕ ПРАВИЛО — НИЧЕГО НЕ ВЫДУМЫВАТЬ.
1. Единственный источник фактов о приборе — входные данные: название, производитель, характеристики, описание.
2. Запрещено добавлять технические сведения, которых нет во входных данных: числа, диапазоны, единицы, классы точности,
   материалы, стандарты (ГОСТ, ТУ, EN, ISO, DIN), степень защиты IP, сертификаты, Госреестр СИ, межповерочный интервал,
   срок службы, гарантию, комплектацию, условия эксплуатации, совместимость, взрывозащиту.
3. Запрещено пересчитывать и «уточнять» значения: не переводи МПа в бар, не округляй, не дописывай допуски.
   Значения характеристик копируй ДОСЛОВНО, символ в символ, как во входных данных.
4. Если характеристика ожидаема для прибора такого типа, но во входных данных её нет, — ставь ровно «данных нет»
   и добавь её в missing_fields с пояснением, зачем она нужна в карточке.
5. Общие сведения о назначении допустимы только в той мере, в какой они следуют из названия и описания
   (например, «манометр измеряет давление»). Области применения формулируй как типовые и осторожно
   («подходит там, где требуется…»), не приписывай прибору свойства, которых нет в данных.
6. Без маркетинговых штампов и обещаний («лучший», «гарантированное качество», «идеальный выбор»), без восклицаний.
7. Поля со значением null или пустой строкой считаются отсутствующими.
```

Дальше — требуемая структура JSON с пояснением каждого поля прямо в значениях-заглушках (лимиты длин
подставляются из констант `app/validation.py`, чтобы промпт и проверка не разъезжались), порядок характеристик
(сначала все из входных данных, потом «данных нет», не больше 6 таких строк) и стиль: русский язык,
адресат — инженер-закупщик.

### Пользовательское сообщение

Входные данные в виде JSON (пустые значения показаны как `null`) плюс чек-лист типовых характеристик КИП
(диапазон, класс точности, присоединение, габариты, материалы, IP, питание, выходной сигнал, температура среды,
климатическое исполнение, межповерочный интервал, Госреестр СИ, срок службы/гарантия). Чек-лист нужен, чтобы модель
осмысленно отмечала «данных нет» — без него она либо молчит об отсутствующем, либо дописывает типовые значения.

### Сообщение с замечаниями (повторная попытка)

Если проверка кодом нашла нарушения, в диалог добавляются предыдущий ответ модели (как `assistant`) и список
замечаний в формате «что не так → что сделать», например:

```
Твой предыдущий ответ не прошёл автоматическую проверку. Нарушения:
- характеристика «класс точности»: значение «1,0» не найдено во входных данных — скопируй значение дословно или укажи «данных нет»
- seo_title: встречаются числа, которых нет во входных данных: 2, 54 — убери их или перефразируй без чисел
- seo_description: 640 символов, нужно 800–1200 — расширь текст, опираясь только на уже имеющиеся факты…

Исправь ответ и верни полный JSON заново, соблюдая все правила. Не добавляй новых фактов: если данных не хватает, используй «данных нет».
```

Замечания формулирует код, поэтому они конкретны и проверяемы — модель исправляет именно то, что не прошло.

## 2. Принятые решения

**OpenAI-совместимый API вместо SDK одного вендора.** Через `LLM_BASE_URL` работает OpenAI, OpenRouter,
корпоративный прокси, vLLM, llama.cpp, Ollama. Для задачи важнее устойчивость пайплайна, чем конкретная модель:
проверки и цикл исправления одинаково работают с облачной и локальной моделью (примеры в `examples/output/`
получены локальной Qwen3.6-35B-A3B через llama.cpp, по 3 обращения на товар).

**JSON-режим + разбор с запасом.** Запрашиваем `response_format=json_object`; если сервер его не поддерживает,
повторяем без него. Ответ терпит markdown-обёртку, разбирается в pydantic-модель `CardDraft`; ошибка структуры —
это тоже замечание для модели, а не падение сервиса. Строгий `json_schema` не использован: его поддерживают не все
провайдеры, а pydantic-валидация после ответа даёт тот же эффект.

**Проверка фактов кодом, а не ещё одним вызовом модели.** Детерминированные проверки дешевле, воспроизводимы
и тестируются без сети. Ключевая — «значение характеристики дословно содержится во входных данных» после
нормализации (регистр, виды тире, десятичная запятая/точка, пробелы вокруг знаков). Она же запрещает пересчёт
единиц: «0–16 бар» вместо «0–1,6 МПа» не пройдёт. Проверка чисел в свободном тексте ловит дописанные гарантии,
IP, годы; список «рискованных» паттернов — утверждения, которые модели особенно любят добавлять.

**Цикл исправления с ограничением.** До 3 обращений к модели на товар (`LLM_MAX_ATTEMPTS`), для локальных
моделей имеет смысл 5: им чаще нужны 2–3 итерации, типичные замечания — оценочные эпитеты («надёжный»),
дописанная «гарантия», длина описания. После исчерпания попыток — безопасные правки кодом и явные
предупреждения, а не тихий выпуск сомнительного текста и не отказ: менеджер получает черновик и знает, что проверить.

**Безопасные правки — только те, что не могут добавить выдумку:** непроверяемое значение → исходное значение
из входных данных (если характеристика нашлась по названию) или «данных нет»; пропущенная характеристика
добавляется как есть. Тексты (описание, заголовок) код не переписывает — только помечает.

**Без few-shot примеров.** Готовый пример карточки повышает риск, что модель перенесёт факты из примера
в ответ, и удорожает запрос. Вместо этого — подробная схема ответа с описанием полей и чек-лист.

**Низкая температура (0.2).** Задача — точный пересказ данных, а не креатив; при 0 некоторые провайдеры
дают более шаблонные запросы и хуже исправляют ответ на повторе.

**Лимит «данных нет» — 6 строк от модели.** Иначе слабые модели выписывают весь чек-лист (питание и интерфейс
у механического манометра), и список характеристик превращается в шум. Пустые характеристики из входных данных
в лимит не входят — они показываются всегда.

**Результат — JSON и Markdown.** JSON для интеграции с CMS, Markdown — для копирования руками; в Markdown
видны длины, пометки «данных нет» и предупреждения. Веб-форма — минимальная, без фреймворков на фронте;
CMS, база и деплой по заданию не нужны.

## 3. Ограничения

- **Проверка подстрокой строга.** Если модель перефразирует значение («резьба G1/2» вместо «G1/2»),
  это нарушение и лишняя попытка. Это осознанно: дословность важнее экономии вызовов, но для некоторых
  форматов (длинные текстовые значения) возможны ложные срабатывания.
- **Проверка чисел не семантическая.** Число, которое есть во входных данных, может быть подставлено не туда
  («класс точности 100»). Частично ловится проверкой характеристик, но в свободном тексте — нет.
- **Утверждения без чисел и вне списка паттернов** («подходит для пищевой промышленности», «совместим с…»)
  код не ловит — только промпт. Для таких случаев нужна вторая модель-проверяющий (см. улучшения).
- **Качество SEO не измеряется.** Запросы формирует модель по здравому смыслу, без данных о частотности;
  плотность ключевых слов не считается.
- **Один товар за запрос, синхронно.** Для каталога из тысяч SKU нужны пакетная обработка, параллельность и кэш.
- **Чек-лист характеристик общий для всех КИП.** Для разных типов приборов (манометры, термопреобразователи,
  расходомеры) уместны разные наборы; сейчас выбор оставлен модели.
- **Только русский язык** и текущие лимиты длин в коде (константы в `app/validation.py`).
- **Локальные модели** дают больше замечаний на первом ответе и иногда несколько многословные комментарии
  в `missing_fields`; качество описания ниже, чем у `gpt-4.1-mini`.

## 4. Возможные улучшения

1. **Второй проход «модель-проверяющий»**: отдельный запрос с вопросом «какие утверждения описания не следуют
   из входных данных?» — закрывает семантические выдумки, которые не ловятся регулярками.
2. **Набор эталонных карточек и регрессионные тесты промпта**: 20–30 товаров с проверенными ответами,
   метрики (доля принятых с первой попытки, число замечаний по типам, длины) — чтобы менять промпт и модель
   не вслепую.
3. **Строгие structured outputs** (`json_schema`, `strict: true`) там, где провайдер поддерживает, — меньше
   попыток на ошибках структуры.
4. **Профили типов приборов**: чек-лист и приоритеты характеристик по категориям (манометр, термометр,
   преобразователь давления, расходомер), сопоставление названий характеристик со словарём магазина.
5. **Данные о спросе** для поисковых запросов (Wordstat, статистика поиска по сайту) и проверка плотности
   ключевых слов в описании.
6. **Пакетный режим**: CSV/XLSX на вход, параллельные запросы, кэш по хешу входных данных, учёт стоимости.
7. **Few-shot из утверждённых карточек магазина** — после того как появится эталонный набор и будет измерено,
   что это улучшает, а не ухудшает точность.
8. **Трассировка и наблюдаемость** (Langfuse или аналог): какие замечания возникают чаще всего — прямой сигнал,
   что поправить в промпте.
9. Экспорт в формат CMS, история версий карточки, редактирование результата прямо в форме.
